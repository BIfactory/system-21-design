# ZÁKLADNÍ PRAVIDLO: PRD ↔ CODE JSOU ZRCADLEM

**Toto PRD je živoucí dokument, ne freeze-dried spec.** Každý sprint / commit / fix co mění chování, UI, data model, komponenty, URL mapu nebo screen flow **musí v stejném PR updateovat tento PRD**.

**Proč to je kritické:**
- Finální stav projektu = perfektní GUI **+** PRD co tomu plně odpovídá a detailně popisuje.
- PRD slouží i jako metodika pro customer overlay projekty (Poema, Tonda Žmola, …) — pokud se rozchází s realitou, nový tým postaví customer verzi proti zastaralé speci.

**Jak to aplikovat:**
- Každý implementation task v plánu má krok "Update PRD" PŘED commit.
- Review subagent v každém reviewu verifikuje že PRD-impacting change má zreflektovanou PRD sekci.
- Final branch review bere PRD jako binding — pokud code ≠ PRD, defaultně **updatujeme PRD** (code je real-world výsledek), jen pokud je code vyloženě chybný → fix code.
- Změny v scope/architektuře → nová položka v sekci "Change log" na konci dokumentu s datem + popisem.

# ČÁST 1 — GLOBÁLNÍ PRD

## 1.1 Proč tohle existuje

System 21 backend je stavěný **univerzálně** — plánuje se nasadit různým zákazníkům, GUI se upravuje per-customer. Tohle demo GUI musí být **referenční univerzální šablona** pro informační a manažerský systém **malé zakázkové firmy**, které:

- mají obchodní pipeline (poptávky → nabídky → podpis)
- realizují zakázky (operace, hodiny, materiál, termín)
- řídí se podle plnění týdenního plánu tržeb
- plánují kapacity lidí
- sledují cashflow
- komunikují s klienty přes email/SMS

Demo se **nezavádí jako jednovládný CEO dashboard**. Je **role-based**: každá role má vlastní "home" obrazovku která ráno ukáže to, co dotyčný právě potřebuje vidět. Sekční moduly (Obchod, Výroba, Lidé, DMS, Cashflow) jsou sdílené napříč rolemi.

## 1.2 Vize v jedné větě

**"Aplikace, která každý den ukáže majiteli zda plní plán tržeb, obchodníkovi kam dál tlačit, vedoucímu výroby jak vytěžuje kapacity, asistentce co dnes vyřídit a pracovníkovi co má dnes dělat — všechno z jednoho datového backbone, bez přepínání mezi nástroji."**

## 1.3 Personas (5 rolí)

Každá persona má **jednu větu motivace** a **co musí vidět první po přihlášení**.

### 1.3.1 CEO / Majitel
**Motivace:** "Plním plán tržeb? Kde nás to táhne dolů?"
**Home ukazuje:**
- Progress týdenního plánu tržeb (např. 420 / 600 tis. Kč, 70 %)
- Čeká tento týden uzavřít (ze zbytkem naplánované výroby)
- Utilizace kapacit (7 lidí × dny, průměr %)
- Top 3 zakázky v riziku (overdue / přetahy / nízká marže)
- Sales pipeline hodnota (open cases)
- Odkaz na detail "Měsíční manažerský přehled" a "Cashflow"

### 1.3.2 Obchodník
**Motivace:** "Co musím tento týden dotáhnout? Mám ještě kam prodávat?"
**Home ukazuje:**
- Sales pipeline s hodnotami (open cases sorted by priority)
- Case velocity + konverze YTD
- **"Capacity-vs-pipeline" chip:** porovnání volné kapacity výroby na 4 týdny dopředu vs. hodnota pipeline → "Výroba má volno, zavřeli bychom víc" nebo "Výroba plná, přibrzdit sales"
- Top 5 cases co dnes potřebují akci (nejvyšší skóre: deadline / hodnota / čas od posledního kontaktu)
- Nové poptávky (unassigned)

### 1.3.3 Vedoucí výroby
**Motivace:** "Kdo dnes dělá co? Máme pokryté týdny dopředu? Co hoří?"
**Home ukazuje:**
- Mini-náhled kapacitní tabulky (tento týden, lidé × dny, barva = utilizace)
- Rizikový list zakázek TOP 5 (overdue / přetahy / nízká marže)
- Odpracováno dnes vs. plán
- Blížící se deadliny zakázek (7 dnů)
- Odkaz na detail /vyroba/kapacita (full planner)

### 1.3.4 Asistentka / Office
**Motivace:** "Co musím dnes vyřídit? Je někdo v práci kdo tam neměl být?"
**Home ukazuje:**
- Fronta AI asistentky — emaily čekající na schválení (TOP 5)
- Docházka týmu dnes (kdo přišel, kdo chybí, dovolené)
- Nové emaily/SMS od klientů (highlight unread)
- Úkoly k dnešnímu dni
- Faktury k nahrání / zpracování

### 1.3.5 Pracovník (konzultant / technik / montér)
**Motivace:** "Co mám dnes dělat? Můžu vykázat čas?"
**Home ukazuje:**
- Dnešní operace přiřazené mně (z kapacitního plánu)
- Shortcut "Vykázat hodinu / Vykázat materiál / Vykázat ad-hoc"
- Moje otevřené úkoly
- Můj fond hodin tento týden (progress bar)
- Kolik hodin už dnes vykázáno

## 1.4 Info architecture

### Sidebar (sdílený napříč rolemi, pořadí fixní)

```
(bez nadpisu)      Domů (/), Můj plán, Úkoly
OBCHOD             Přehled, Obchodní případy, Klienti, Osoby
VÝROBA             Přehled, Zakázky, Kapacita, Vykazování
LIDÉ               Přehled, Pracovníci, Docházka
DMS                Přehled, Smlouvy, Dokumenty, Automatizace / AI
CASHFLOW           Přehled, Rozpočet, Výdaje, Banka
```

**Pozn.:** "Domů" je top-level, ale **obsah se renderuje per role** — tj. `/` není jedna fixní stránka, ale shell co podle role načte správný "home" component.

**Komunikace / Intranet** — pryč ze sidebaru (jak již v předchozí restrukturalizaci), zůstávají v topbar bell + `/inbox`.

### Topbar (sdílený)

```
Breadcrumbs | Search (global) | InboxBell | NotificationCenter | BrandToggle | ThemeToggle | PersonaSwitcher | Avatar
```

**PersonaSwitcher** — **nová komponenta pro demo**. Dropdown s 5 rolemi; klik přepne aktuální role, re-renderuje `/` home. V produkci (customer deploy) tato komponenta zmizí — uživatel má jen svou roli z backendu. Ve demo je demonstrativní "zkus různé pohledy".

### Zoom level model (nezměněno z MIS restruktruralizace)

```
Firma (role home)
  → Sekce landing (/obchod, /vyroba, /lide, /dms, /cashflow)
    → Operativa list (/obchod/klienti, …)
      → Detail (/obchod/klienti/[slug], …)
```

Operativa + detail jsou **stejné pro všechny role** — persona ovlivňuje jen home a případně výchozí zobrazení.

## 1.5 Design principy

1. **Minimalism — v dekoraci, ne v obsahu.** Žádné FAB, bannery, pestré barvičky. Ale ano všechno co firma potřebuje vidět.
2. **Zoom level drill-down.** Home → sekce → list → detail. Žádné "mode" přepínače IS vs MIS.
3. **Čeština only, CZ formát.** `12 345 Kč`, `12. 04. 2026`.
4. **Data-driven.** Všechny hodnoty na dashboardech se počítají z `_shared-data.js` (CASES, ORDERS, atd.) + nové datové vrstvy pro kapacitu a cashflow.
5. **Role-based home, shared ostatek.** Jedinou role-specific obrazovkou je `/`. Zbytek je neutrální.
6. **Universal terminologie.** Žádné Poema-specific výrazy. "Smlouva" ne "pojistka", "zakázka" ne "polep", "klient" ne "pojištěnec".
7. **Mobile-first ověřené.** Všechny nové obrazovky testovány na 375 px desktop prostor, žádný horizontal overflow.

## 1.6 Non-goals

- Nejsou nové ERP koncepty jen kvůli demu (žádný CRM campaign management, žádný marketing automation, žádný helpdesk).
- Není skutečná business logic — všechno je mock. "Uložit změnu" neukládá, jen zobrazí toast.
- Není multi-tenant admin — jedna firma per demo.
- Není mobile app — responsive web only.

## 1.7 Anti-goals (čemu se vyloženě vyhýbáme)

- Uživatel nemůže zablbnout že "systém řekne jestli plním plán" tím že dashboard ukáže něco jiného podle nálady. Deterministický, jednoznačný.
- Role switcher nesmí být složitější než "klik → re-render". Žádný wizard, žádný "set-up your role".
- Kapacitní plánování nesmí být Gantt chart. Je to **týdenní tabulka** (lidé × dny) protože to je UX který malé firmy znají z whiteboardu / Excelu.
- Cashflow modul není účetní software. Žádné faktury, žádné DPH, žádné rozpočtové podklady. Jen manažerský pohled.

## 1.8 Omezení (co nemůžeme změnit)

- Plain React 18 + `window.S21` UMD global, žádný bundler per stránku. Design tokens + brand overlay zachovány.
- Mock data zůstávají konzistentní — stejní klienti (Novákovi, Dvořákovi, Moravia Steel, Agro Slovácko, Hradecká strojírna).
- Čeština only.
- Playwright před commit (desktop 1440 + mobile 375, 0 console errors).
- Push na main čeká na user approval.
- **Repo:** všechna práce v `/Users/hulin/3_Dev/reseni/system-21-design/` (adresář `system21-demo-gui/` je jen working-dir reference, obsahem prázdný). Všechny HTML stránky žijí v `demo/`, sdílená data v `demo/_shared-data.js`.

## 1.9 Zvažované přístupy (klíčová rozhodnutí)

### 1.9.1 Role-based dashboard architektura

**A) Shell + variant components** (zvoleno)
Jeden `/dashboard.html` nebo `/index.html` + React shell co podle `localStorage.getItem('system21-role')` renderuje `CEODashboard`, `ObchodDashboard` atd. PersonaSwitcher v topbar mění stav + re-renderuje.
Pro: jedna URL, žádný routing, demo vhodné. Minimální přidaná složitost.
Proti: komponenty žijí v jednom HTML souboru (> 500 řádků) — řešitelné split do dílčích JS souborů.

**B) Multi-URL per role** (`/dashboard/ceo.html`, `/dashboard/obchod.html` …)
Pro: čisté soubory, snadno sdílet linkem "koukni na obchodníkův home".
Proti: 5 souborů, duplicita shellu, PersonaSwitcher by musel navigovat URL místo stateu.

**C) Server-side role resolution**
V demo nedává smysl (není server). Vynecháno.

**Zvoleno A.** Reason: nejmíň souborů, demo-friendly, role state je trivial `useState` + localStorage.

### 1.9.2 Kapacitní plánování

**A) Gantt chart** — řádky = lidé, kalendářová časová osa, operace jako barevné bary s drag/drop.
Pro: nejvizuálnější, "wow efekt".
Proti: Gantt knihovna je komplexní, custom je ~2 týdny práce, naučená křivka vysoká, mobile nemožné.

**B) Týdenní tabulka** (zvoleno) — řádky = lidé (7), sloupce = pracovní dny týdne (po-pá), buňky obsahují chip s operacemi; klik na buňku otevře picker.
Pro: UX co malé firmy znají (whiteboard, Excel). Kratká křivka. Mobile = horizontal scroll.
Proti: méně vizuálně "wow"; pro multi-week view musí user přepínat týden.

**C) Formulář / list** — pouhý seznam operací s dropdownem "kdo/kdy". Nejrychlejší postavit.
Proti: nejslabší UX, nedává overview.

**Zvoleno B.** Reason: realistická přístupnost + rozumná práce.

### 1.9.3 PRD struktura

**A) Jeden dokument** (zvoleno) — PRD + metodika + per-screen specs v jednom souboru.
Pro: jedno místo pravdy. Snadné pro customer overlay projekty mít "jediný odkaz".
Proti: dlouhé; sections navigate přes anchors.

**B) Rozdělit PRD + methodology do dvou souborů**
Pro: každá vrstva má vlastní kadenci updatů.
Proti: bude je pokaždé potřeba konzultovat obě; v praxi vyjde komplikovaněji.

**Zvoleno A.** Reason: pro malou organizaci je jeden dokument = jediný pointer, méně zmatku.

### 1.9.4 Cashflow modul — rozsah

Cashflow je nová sekce (v předchozí restrukturalizaci nebyla). Rozsah:

**A) Full accounting-like** — faktury, DPH, rozvaha.
Odmítnuto — není ERP.

**B) Manažerský pohled** (zvoleno) — příjmy (ze zakázek + historické), výdaje (plán + skutečnost), zůstatek bank účtů (mock), graf 12 měsíců forecast.
Pro: dost na to aby CEO viděl "dojde mi za 3 měsíce peníze?".

**C) Jen link na externí nástroj** (např. Fakturoid)
Pro: žádná práce. Proti: narušuje "jeden end-to-end systém" narativ.

**Zvoleno B** s lightweight scope — 1 landing screen pro teď, detailní budget/banka jako placeholder.

# ČÁST 2 — PER-SCREEN SPECIFIKACE

## 2.1 Template vyplňování

Každá obrazovka má tuto strukturu:

```
### [URL + lidský název]

**Co vyjadřuje (message)** — jaké klíčové sdělení obrazovka předává (jedna věta).

**Data** — odkud se berou mock data.
**Overlay poznámka** — co customer deploy typicky mění.
```

   - Řádky = **pracovníci (7)**, sloupce = **pracovní dny (po-pá)**.
   - Každá **buňka** = součet přiřazených operací v hodinách + barva podle utilizace:
     - šedá: 0-20 % (volno)
     - zelená: 20-80 % (OK)
     - jantarová: 80-110 % (plno)
     - červená: > 110 % (přetížení)
   - Hover buňky: tooltip s rozpadem operací.
   - Klik na buňku: otevře side-drawer s detailem toho dne pro toho člověka + list operací + možnost přidat/odebrat.

3. **Side-drawer při kliku na buňku:**

   - Formulář "Přidat operaci" → SearchSelect zakázka → SearchSelect operace → Input hodiny → Uložit

4. **Spodní pruh "Pokrytí dopředu":**
   - 4 týdny dopředu, průměrná utilizace: "Tento týden 72 % · +1 73 % · +2 68 % · +3 45 % · +4 12 %"
   - Když klesá pod 30 % v některém týdnu: warning "Nemáme co plánovat".

5. **Spodní tabulka "Nepřiřazené operace":**
   - Operace ze zakázek v realizaci, které ještě nemají přiřazeného člověka ani den.

# ČÁST 3 — METODIKA PRO CUSTOMER OVERLAY

## 3.1 Co customer overlay typicky mění

Když se demo klonuje jako "Poema", "Tonda Žmola" atd., zákaznická verze typicky:

1. **Branding** — barva, logo, název, favicon (`[data-brand=poema]` override v tokens.css).
2. **Terminologie** — "smlouva" → "pojistka", "zakázka" → "lepárna", "klient" → "pojištěnec" (hunt/replace v demo/*.html).
3. **Data a persony** — nahradit Novákovi / Moravia Steel atd. za zákazníkova data.
4. **Role mix** — mít jen některé role (např. pojišťovák potřebuje jen Obchodník + Asistentka + CEO).
5. **Sekce visibility** — některé moduly skrýt (např. pojišťovák nepotřebuje `/vyroba/kapacita` v klasické formě).
6. **Dashboard varianty** — upravit obsah CEO home podle byznysu zákazníka (jiné KPI, jiné vzorce plnění plánu).

## 3.2 Co zůstává nedotčené (library layer)

Nikdy se při customer overlay neupravuje:

- `src/components/index.jsx` — knihovna komponent (neutrální tokens-based).
- `src/components/bundle.css` — styling knihovna.
- `tokens/tokens.css` — tokens definice (jen override hodnot v brand sekcích).
- `_shared.js` v demo/ — topbar/sidebar wrapper (neutrální).
